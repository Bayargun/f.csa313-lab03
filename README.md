## PASS тестийн үр дүн

20 VU, 1 минутын ачааллын тестээр дараах үр дүн гарсан.

| Үзүүлэлт            | SLO          | Бодит үр дүн    | Төлөв |
| ------------------- | ------------ | --------------- | ----- |
| `/cart/add` latency | p95 < 2 ms   | p95 = 1 ms      | PASS  |
| `/report` latency   | p95 < 450 ms | p95 = 388.93 ms | PASS  |
| `/pay` error rate   | < 8%         | 3.54%           | PASS  |
| Checks              | > 90%        | 98.81%          | PASS  |

`/cart/add` endpoint-ийн эхний хэмжилтээр p95 = 1.11 ms орчим
гарсан тул хэт сул босго сонгохоос зайлсхийж p95 < 2 ms гэсэн
Performance SLO сонгосон. Эцсийн PASS туршилтаар p95 = 1 ms
гарсан бөгөөд босгыг хангасан.

/report endpoint нь зориудаар 200–400 ms сааталтай тул
p95 < 450 ms босго сонгосон. Туршилтаар p95 = 388.93 ms
гарч босгыг хангасан.

/pay endpoint нь ойролцоогоор 5% санамсаргүй алдаа үүсгэхээр
хийгдсэн тул error rate < 8% босго сонгосон. Туршилтаар
error rate = 3.54% гарсан бөгөөд Reliability SLO-г хангасан.

## Chaos test

Chaos туршилтыг 20 VU, 2 минутын хугацаатай ажиллуулсан.
Туршилтын үед серверийг зориудаар 10 секунд зогсоож дараа нь
дахин асаасан.

| Үзүүлэлт                | SLO          | Бодит үр дүн | Төлөв |
| ----------------------- | ------------ | ------------ | ----- |
| `/cart/add` latency     | p95 < 2 ms   | 1.04 ms      | PASS  |
| `/report` latency       | p95 < 450 ms | 389.77 ms    | PASS  |
| Availability (`checks`) | > 90%        | 78.23%       | FAIL  |
| `/pay` error rate       | < 8%         | 24.48%       | FAIL  |

Нийт 5820 check-ээс 4553 нь амжилттай, 1267 нь амжилтгүй
болсон. Иймээс request-based availability:

Availability = 4553 / 5820 × 100 = 78.23%

Availability SLO нь 90%-иас дээш байх ёстой байсан тул chaos
туршилтын үед availability threshold FAIL болсон.

2 минут цонхонд 90% availability SLO-ийн
time-based error budget:

120 × (1 - 0.90) = 12 секунд.

Серверийг ойролцоогоор 10 секунд зогсоосон нь time-based
12 секундын error budget-аас бага боловч request-based
availability 78.23% болсон. Учир нь сервер унтарсан үед
хүсэлтүүд connection refused алдаатайгаар маш хурдан буцдаг.
Иймээс богино хугацаанд олон failed request үүсэж,
request-based availability нь time-based availability-аас
доогуур гарсан.

Мөн /pay endpoint-ийн error rate 24.48% болж, 8%-ийн
Reliability SLO-г зөрчсөн. Сервер унтарсан үед /pay хүсэлтүүд
мөн амжилтгүй болсон учраас нэг серверийн эвдрэл availability
болон reliability SLO-д хоёуланд нь нөлөөлсөн.

### FAIL тестийн үр дүн

### FAIL тест ба Exit Code

`/report` endpoint-ийн threshold-ийг зориуд `p(95) < 100 ms`
болгон FAIL тест хийсэн.

Туршилтын үр дүн:

- `/cart/add` p95 = 932.08 µs — PASS
- `/report` p95 = 389.23 ms — FAIL
- `/pay` error rate = 5.79% — PASS
- checks = 98.06% — PASS
- k6 exit code = 99

`/report` endpoint нь 200–400 ms зориудын сааталтай тул
`p(95) < 100 ms` босгыг хангаж чадаагүй. Үүний улмаас k6
`http_req_duration{name:report}` threshold зөрчигдсөнийг
илрүүлж, exit code 99 буцаасан. CI/CD pipeline нь ийм non-zero
exit code-ийг ашиглан тест амжилтгүй болсныг илрүүлж build-ийг
зогсоох боломжтой.

## Дүгнэлт

Энэ лабораторийн ажлаар чанарын сценариог SLO болгон тоон
хэмжүүрээр илэрхийлж сурлаа. Performance, reliability болон
availability чанарын үзүүлэлтүүдийг тус тусад нь тодорхойлсон.
SLO-г k6 threshold болгон хөрвүүлснээр шаардлагыг автоматаар
PASS болон FAIL хэлбэрээр шалгах боломжтой болсон. Performance
threshold сонгохдоо бодит p95 хэмжилтэд тулгуурлан `/cart/add`
endpoint-д p95 < 2 ms босго сонгосон. Chaos туршилтаар серверийг
10 секунд зогсооход availability 78.23% болж SLO зөрчигдсөн.
Мөн `/pay` error rate 24.48% болж reliability threshold зэрэг
FAIL болсон. Time-based error budget болон request-based
availability хооронд ялгаа гарч болохыг туршилтаар харсан.
Зориуд `/report` threshold-ийг p95 < 100 ms болгосноор k6
threshold зөрчигдөхийг автоматаар илрүүлж байгааг шалгасан.
Ингэснээр scenario → SLO → threshold гэсэн холбоог практик
туршилтаар ойлгосон.

### AI-ийн хариунд хийсэн үнэлгээ

AI нь Performance сценариод `/cart/add` endpoint-ийн p95 < 5 ms гэсэн
тоон босго санал болгосон боловч бодит туршилтаар p95 = 1 ms орчим
гарсан тул энэ босго харьцангуй сул байсан. Өөрийн SLO-д бодит
хэмжилтэд тулгуурлан p95 < 2 ms босго сонгосон нь илүү нарийн
шаардлага болсон. Reliability сценариод AI-ийн санал болгосон
error rate < 8% нь `/pay` endpoint-д зориудаар ойролцоогоор 5%
алдаа үүсгэдэгтэй нийцэж байсан тул бодитой босго гэж үзсэн.
Availability сценариод серверийн crash-ийг гадаад өдөөлт болгон зөв
тодорхойлсон бөгөөд recovery хугацааг 10 секундээр хэмжих санал нь
chaos туршилттай тохирсон. Гэхдээ AI нь сервер унтарсан үед
connection refused хүсэлтүүд маш хурдан үүсэж, request-based
availability болон time-based error budget хооронд ялгаа гарахыг
урьдчилан тодорхой тайлбарлаагүй. Миний өөрийн сценарио бодит k6
хэмжилтийн үр дүнд тулгуурласан тул Performance босгыг илүү нарийн
тодорхойлсон бол AI-ийн хувилбар сценариогийн 6 хэсгийг илүү
цэгцтэй, ойлгомжтой бүтэцтэй болгосон давуу талтай байсан.

## 2. SLO

| Сценарио           | SLI (юуг хэмжих)                  | Босго        | Цонх / нөхцөл                                  |
| ------------------ | --------------------------------- | ------------ | ---------------------------------------------- |
| Performance        | `/cart/add` хүсэлтийн p95 latency | p95 < 2 ms   | 20 VU, 1 минут                                 |
| Reliability        | `/pay` хүсэлтийн error rate       | < 8%         | 20 VU, 1 минут                                 |
| Availability       | Амжилттай checks-ийн хувь         | > 90%        | 20 VU, 2 минут, 10 секундийн серверийн зогсолт |
| Report Performance | `/report` хүсэлтийн p95 latency   | p95 < 450 ms | 20 VU, 1 минут                                 |

### Босго сонгосон үндэслэл

`/cart/add` endpoint-ийн анхны хэмжилтээр p95 = 1.11 ms орчим
гарсан тул хэт сул босгоос зайлсхийж p95 < 2 ms гэж сонгосон.
PASS туршилтаар p95 = 1 ms гарч уг босгыг хангасан.

`/pay` endpoint нь кодын дагуу хүсэлтүүдийн ойролцоогоор 5%-д
алдаа зориудаар үүсгэдэг. Иймээс санамсаргүй хэлбэлзлийг
тооцож error rate < 8% босго сонгосон.

`/report` endpoint нь 200-400 ms зориудын сааталтай тул
p95 < 450 ms босго сонгосон.

### Availability Error Budget

Availability SLO = 90%

Тестийн хугацаа = 2 минут = 120 секунд

Error budget = 120 × (1 - 0.90) = 12 секунд

Иймээс 2 минутын цонхонд систем хамгийн ихдээ 12 секунд
unavailable байх боломжтой.
